## 4. Problemas corrigidos
1. **`--json` corrompido:** a redação agia sobre o JSON já serializado e consumia `",`, além de mutilar `<não exibida>`. Agora `sanitizeForOutput`/`toSafeJson` (`url-redaction.ts`) sanitizam cada valor **antes** de serializar (link saneado passa intacto, link inteiro → forma saneada, texto → redação, chaves sensíveis → `[REDACTED]`, listas sem truncar, `__proto__` inofensivo). O cabeçalho `X-API-KEY` agora sai `[REDACTED]`.
2. **Identificadores:** novo bloco `identifiers` = `fromLink` × `derived` × `returnedByProvider` × `confirmed[]` (tipo, valor, origem do esperado, campos do provedor usados, `EQUAL`); `provenIdentifiers` passa a significar "efetivamente comparado e confirmado" (no caso real, `{cid: <CID>}`); o `placeId` retornado não é declarado comprovado (o link não o tinha); o FID só é "igual" se igual por inteiro.
3. **Site:** `site-provider.ts` não trata mais 401/403 como erro de segurança; o código real é preservado e os sinais (desafio `WWW-Authenticate`, caminho de login recusado, limite de requisições) ficam registrados. `assessSiteAccess` (`collector/site-access.ts`) classifica: `REACHABLE`, `UNREACHABLE`, `BLOCKED_BY_SAFETY`, `LOGIN_PATH_BLOCKED`, `REQUEST_LIMIT`, `HTTP_401`, `HTTP_403`, `AUTH_REQUIRED_EVIDENCED` (**só** 401 + desafio), `HTTP_OTHER`, `NOT_HTML`, `RESTRICTED_RESPONSE_UNSPECIFIED` (somente o run original). Nenhum texto diz que o site "exige login" sem evidência; 403 diz "não prova que o site exija login". `site-check.ts` não foi alterado; SSRF, teto de 8 requisições e bloqueio de login permanecem.
